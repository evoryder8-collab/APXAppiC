# What users can experience

The examples below identify whether the finding was reproduced with the shipped calculations and synthetic data, measured in the live public catalogue, or traced through the application source.

## Editing food and finding it again

**An ordinary edit can lose ingredients.** The dashboard loads up to 360 meal headers and the latest 1,000 ingredient rows in separate requests. The editor reconstructs its draft from those rows. Its save operation replaces the stored meal. In an isolated database with 334 meals and 1,001 ingredients, the older of two ingredients disappeared from the editable draft. Changing the visible ingredient from 100 g to 110 g left only that ingredient on the server. A dedicated fetch by owner and meal ID should load the whole edit. A version check should reject replacement if another device edited the meal meanwhile. [Dashboard queries](../../../../ios/APEXNative/APEX/Core/Networking/SupabaseService.swift#L423) · [Editor](../../../../ios/APEXNative/APEX/Features/Nutrition/MealComposerView.swift#L1037) · [Database replacement](../../../../supabase/migrations/20261106213648_recovery_meal_slot_compatibility.sql#L44)

**A more specific food query can produce fewer useful matches.** With the Swiss product record, the server ranker and native Swift both matched “Cheeseburger Royal.” The server also matched “McDonald’s Cheeseburger Royal,” while the native ranker removed the result when given the brand and product name together. The same happened for “KFC Colonel Original.” iOS re-ranks successful server results and looks for the search terms in individual fields. Match across product name, brand and aliases, while preserving the existing owner and hidden-food filters. In the live source catalogue, “oil” returned extra virgin olive oil first, “bread seeds” returned seeded bread first, and “bread sunflower” returned three sunflower breads. The first three source results for “steak” were pudding, fries and sauce. A plain cut of meat is a better default for that query. The source ranking is only one input to the personalised iPhone list. [Native matching](../../../../ios/APEXNative/APEX/Core/Engine/MealMemory.swift#L274) · [Server-result merge](../../../../ios/APEXNative/APEX/App/AppSession.swift#L4636) · [Shared server ranker](../../../../shared/foodSearchRanking.ts)

**Extreme pasted quantities can crash a portion preview.** A Swift probe using the app’s parser and portion arithmetic accepted a 20-digit quantity and returned a finite calorie total too large to represent as an integer. The preview uses a trapping integer conversion before the user can save. Validate the input and safely format the computed result. [Amount preview](../../../../ios/APEXNative/APEX/Features/Nutrition/FoodAmountSheet.swift#L499)

## Training and the daily dashboard

**Viewing a finished workout can write back a different load.** In the iPhone recovery test, the user repaired a draft, triggered one simulated disk-write failure, reopened it and tapped Save. Opening the resulting receipt populated its numeric editors. Their text-change handlers then called the write path without any manual edit. The debug fixture terminated when it caught an attempted remote replay. The production editor uses the same binding and rounds noninteger values to one decimal place on display, so a stored 1.25 kg load can be rewritten at lower precision just by viewing it. The release build does not contain the fixture's deliberate crash. Separate rendering from user edits, discard semantically unchanged writes, and test opening and closing a receipt with a fractional load. [Field initialization and writeback](../../../../ios/APEXNative/APEX/Features/Training/ExerciseFactFieldsView.swift#L206) · [Receipt binding](../../../../ios/APEXNative/APEX/Features/Training/WorkoutReceiptSheet.swift#L282) · [Queue flush](../../../../ios/APEXNative/APEX/App/AppSession.swift#L6044)

**Quick Log needs one receipt per draft.** Unlike guided completion, the manual logger leaves Save enabled during asynchronous writes and creates a fresh receipt ID on every invocation. Two taps before dismissal can produce two receipts, both counted by Insights. This is a source-traced race. Give the draft an ID once, reuse it at the write boundary and disable the button immediately. Test with the first save deliberately delayed. [Manual Save](../../../../ios/APEXNative/APEX/Features/Training/ManualWorkoutLoggerView.swift#L109) · [Receipt construction](../../../../ios/APEXNative/APEX/App/AppSession.swift#L7370) · [Insights](../../../../ios/APEXNative/APEX/Core/Engine/WorkoutInsights.swift#L28)

**A completed workout and a recurring template share the wrong identity.** For an unscheduled Quick Log, the app picks the first custom program day for the same weekday or creates an active “Manual workout” day. That empty day can appear in the custom workout list and trigger a replacement prompt when someone later schedules a real workout. Simple has the opposite problem: it selects one guided program, so a separately scheduled custom workout is absent from that day’s list. Both paths were traced in source. Use an explicit optional link from a receipt to a prescribed session. Build the daily list from all eligible scheduled sessions. [Quick Log weekday selection](../../../../ios/APEXNative/APEX/App/AppSession.swift#L7335) · [Simple daily list](../../../../ios/APEXNative/APEX/Features/Portal/SimpleHomeView.swift#L170) · [Custom builder](../../../../ios/APEXNative/APEX/Features/Training/CustomWorkoutBuilder.swift#L170)

**The chosen screen changes whether a future workout can be marked complete.** The calendar detail guards future dates. Quick Log’s date picker has no upper bound, and Advanced can start a future weekday’s template and pass its date to the completion writer. Offer “Train this workout today” when selecting a future prescription. Validate the performed date at the shared write boundary. [Date picker](../../../../ios/APEXNative/APEX/Features/Training/ManualWorkoutLoggerView.swift#L63) · [Advanced player entry](../../../../ios/APEXNative/APEX/Features/Training/TrainingProgramView.swift#L1539) · [Completion writer](../../../../ios/APEXNative/APEX/App/AppSession.swift#L5760)

## Avatar and nutrition feedback

**Missing evidence can look like declining fitness.** A standard synthetic account with no assessed movement domains began with 50.8 overall, 60 upper-body strength and 42 lower-body strength. With identical inputs, 31 days later its overall was 39.8. The production view reads snapshots from the legacy calculation. Standard accounts can inherit a named persona’s starting point, and uncovered days decay toward a floor. Both the production Swift engine and its TypeScript counterpart reproduced the numbers. The evidence-aware model currently runs in shadow mode. Keep unassessed scores visibly unknown and validate individual domains before changing which model is published. [Onboarding expectation](../../../../ios/APEXNative/APEX/Features/Onboarding/InductionView.swift#L833) · [Published snapshots](../../../../ios/APEXNative/APEX/App/AppSession.swift#L2093) · [Daily decay](../../../../ios/APEXNative/APEX/Core/Engine/FitnessBrainEngine.swift#L639)

**Daily feedback can contradict the user’s actual target or incomplete diary.** For the same T25 workout, 2.0 L consumed against a 2.0 L goal received no hydration credit. At 2.5 L against a 3.5 L goal it earned the “Hydration at target” bonus. The avatar checks a fixed 2.5 L. In a strength example, recording only a 400 kcal breakfast changed lower-body strength from 44.0 to 43.7 and generated a deep-deficit message. Using the personalised goal for that date and deferring deficit judgments until intake is sufficiently evidenced would remove both contradictions. The nutrition target itself uses baseline expenditure, so logging a workout does not automatically add its burn to the food allowance. [Personal hydration goal](../../../../ios/APEXNative/APEX/Core/Engine/HydrationLedger.swift#L56) · [Avatar rules](../../../../ios/APEXNative/APEX/Core/Engine/FitnessBrainEngine.swift#L465) · [Nutrition targets](../../../../ios/APEXNative/APEX/Features/Nutrition/EnergyEngine.swift#L483)

**A perfectly regular meal schedule can appear irregular.** The native calculation gave 150 minutes of variation and 81.25/100 for 14 identical days of a 16:00 snack and a 21:00 recovery meal. Both use the storage slot `snack`, though the meal’s original kind is preserved. The calculation also accepted three future breakfasts in today’s window. Group by the existing logical meal kind and bound the window at both ends. The empty-state copy should explain that timing variation requires repeated observations of a comparable meal. [Logical meal identity](../../../../ios/APEXNative/APEX/Core/Engine/MealBlocks.swift#L24) · [Eating-pattern calculation](../../../../ios/APEXNative/APEX/Features/Avatar/AvatarView.swift#L735)

## Account lifecycle, coaching and legibility

**Account controls are incomplete.** Email sign-in offers registration and authentication but no password reset. Account Settings offers logout. The privacy text says users may request account deletion, but there is no in-app action or direct deletion link. This matters before a commercial release. Add a recoverable email flow and a confirmed deletion entry under Account, then exercise both with a disposable account. This audit did not establish the cause of any TestFlight distribution error. [Sign-in form](../../../../ios/APEXNative/APEX/Features/Auth/EmailAuthView.swift#L95) · [Account settings](../../../../ios/APEXNative/APEX/Features/Settings/SettingsView.swift#L657) · [Privacy text](../../../../ios/APEXNative/APEX/Features/Onboarding/InductionView.swift#L1154) · [Apple’s account deletion guidance](https://developer.apple.com/support/offering-account-deletion-in-your-app/)

**The coach plan editor can strand a draft.** The editor permits an eighth session but provides removal only for exercises. The app and server reject plans with more than seven sessions, even as drafts. A coach can therefore lose unsaved work. Show the seven-session limit on Add and provide a session removal control. [Editor](../../../../ios/APEXNative/APEX/Features/Coach/CoachWorkspaceView.swift#L408) · [Server rule](../../../../supabase/migrations/045_coach_platform_foundation.sql#L310)

**New-subscriber onboarding has no draft after process termination.** First-run answers live in view state until the final Build action. The avatar calibration questionnaire already has an account-scoped resumable draft. Use its pattern after consent, and test interruption, completion and sign-out. [Induction state](../../../../ios/APEXNative/APEX/Features/Onboarding/InductionView.swift#L12) · [Existing resumable form](../../../../ios/APEXNative/APEX/Features/Avatar/BaselineCalibrationSheet.swift#L820)

**The main action can be hard to read.** A fresh iPhone screenshot of “Your normal week” showed white Continue lettering on amber. The contrast was 1.87–1.93:1 at three rows through the lettering, sampled against the adjacent gradient. That falls below even the 3:1 large-text benchmark. White against the declared base teal also measures 2.45:1. The existing dark ink gives 9.26:1 against base amber and 7.55:1 against base teal. Choose label color per fill, then recheck the rendered gradient and larger text sizes.
